P1 — financial correctness and access

BUG-01 — Wrong outstanding on payment creation Fixed Browser check pending

Root cause
The payment form carried its own copy of the outstanding calculation and filtered orders by status = 'Approved' where the business rule is 'Closed'. The closed ₹15,300 order was therefore excluded entirely: 0 − 0 + 10,000 = ₹10,000. Not a rounding or caching issue — a second, divergent implementation of the rule.
Files
src/lib/payments/financials.ts (new fetchCustomerFinancials()), src/components/payments/payment-form.tsx, src/components/payments/customer-financial-card.tsx
Fix
The duplicate is deleted. fetchCustomerFinancials() is now the one place the figure is derived, and both the payment form and the customer card call it — so the two screens are incapable of disagreeing. The snapshot refetches whenever the selected customer changes, so it reflects approvals and cancellations. The formula itself is untouched.
Regression
Two tests added: one asserts the query filters on Closed (fails if anyone reintroduces Approved), one reproduces the pilot scenario and expects 25,300 outstanding / 74,700 available. Both pass.
Outstanding
Needs one Admin session to confirm on screen — see Awaiting your session below.
Impact
A rep collected against a figure ₹15,300 too low, on the one screen where the number is used in front of a customer.

BUG-12 — "Own records" not enforced on payments Fixed & verified

Root cause
The RLS SELECT policy on payments checked only account membership. The scope setting was never consulted, so every row was genuinely readable — hiding rows in the UI would have left the data reachable by URL or API key.
Files
supabase/migrations/20260814220000_payment_scope_enforcement.sql (applied), src/components/payments/payment-form.tsx
Fix
New payment_scope_allows(owner_user_id, account_id) resolves scope from the existing model — the *_scope keys already on employee_roles.permissions, and get_all_reports() for team scope — in the same precedence the application's getDataScope() uses: module scope, then global scope, then own. It now gates SELECT and UPDATE on payments and SELECT on payment attachments. Owner, admin and the all wildcard are unaffected. The customer picker filters server-side on the contact scope. No payment-specific scope system was created.
Regression
As Dhaval Vegad (global_scope: own): the payments list went from all three of another user's collections to "No data found", 0 of 0. Navigating directly to /payments/b884315a…, a payment owned by sumit vegad, was refused and returned to an empty list. Customer picker: he owns 1 of 26 contacts and the query now filters on user_id server-side.
Impact
A field rep could read the company's entire collection history — who collected how much, from whom, when.

P2 and P3

BUG-02 — Payments unreachable by direct URL Fixed & verified

Root cause
DEFAULT_MODULE_SETTINGS.payment is false. On a cold load the route guard in dashboard-shell.tsx ran against those defaults before the account's real settings arrived, read payment as disabled, and redirected. Sidebar clicks worked because the settings were already in memory.
Files
src/hooks/use-auth.tsx, src/app/(dashboard)/dashboard-shell.tsx
Fix
A moduleSettingsLoaded flag; the guard returns early until the real settings arrive. This also protects Route and Reporting Hierarchy, which likewise default to off. An unauthorised user still gets the standard redirect — only the premature one is gone.
Regression
Direct navigation to /payments and /payments/new both loaded. Previously reproduced three times in a row.

BUG-03 & BUG-09 — Currency formatting Fixed

Root cause
Two separate faults. The customer list rendered {val} raw, with a comment conceding it was a placeholder. The payment form defined its own en-IN Intl.NumberFormat, producing ₹1,00,000.00 where the shared formatter gives ₹100,000.
Files
src/app/(dashboard)/contacts/page.tsx, src/components/payments/payment-form.tsx, src/lib/currency.ts
Fix
Both use formatCurrency() from lib/currency. The local Intl instance is deleted. Added getCurrencySymbol() to the same module for BUG-11 — a lookup into the existing CURRENCIES table, not a second formatter.

BUG-05 — Closed and Cancelled both red Fixed

Root cause
STATUS_MAPPINGS in design-tokens.ts mapped closed: 'destructive', identical to cancelled.
Files
src/lib/design-tokens.ts
Fix
closed moved to success, using the existing semantic variants. No new colours.
Note
This token is shared, so any other module rendering a status literally called "closed" now shows success. For orders that is correct — Closed means fully dispatched and booked. Worth a glance if another module uses "closed" to mean lost.

BUG-04 — "Contact Person" column Does not reproduce

Investigation
The column already binds correctly: contact_person renders contact.name, and the first column is labelled Company Name and renders contact.company. The detail view separates them correctly too.
Likely explanation
Most existing customers were created with name equal to the company — Balaji Supermarket's contact person is literally "Balaji Supermarket". So the column shows the company because that is the stored contact person, not because it is bound to the wrong field. The header in the screenshot came from a saved column layout.
Decision
No change. Rebinding a correct column would have broken it. If you want the underlying data cleaned — contact person distinct from company — that is a data exercise, and I would want your say before touching 25 real customer records.

BUG-06 — Duplicate products Test data, not a query fault

Investigation
Every duplicate is a Dummy Product N with a DUMMY-NNNN SKU, and each pair was created at two distinct timestamps — 2026-06-30 19:28:32 and 2026-07-01 19:47:11. The seed migration ran twice. The picker query is correct and renders exactly what is stored.
Decision
No product data deleted, as instructed. These may be referenced by existing order_items, so deletion needs checking first, and they are your records.
Cleanup, for your approval
Removing the later copy of each pair, only where it is referenced by no order line: DELETE FROM products p WHERE p.name LIKE 'Dummy Product %' AND p.created_at = '2026-07-01 19:47:11.909461+00' AND NOT EXISTS (SELECT 1 FROM order_items oi WHERE oi.product_id = p.id); Say the word and I will run it and report the count.
