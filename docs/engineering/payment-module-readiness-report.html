Payment Module Readiness

A production-readiness review of the Payment Collection module, following a production data incident discovered during the same session.

14 August 2026 Web fix/payment-module-production-readiness Mobile feat/mobile-payment-collection

Bottom line

The module was not production ready, and was not partially working — it was not working at all. Payment creation failed on both web and mobile from the day it shipped, for the same class of reason: the code wrote to columns that do not exist. The shipping commit (a03b22a) described it as “Complete end-to-end payment collection flow” with “Credit Limit & Credit Days enforcement” and “Ready for Pilot”. None of those three claims was true.

The three payments in production were created before the current code landed. No customer has ever successfully collected money through this module.

Both clients now work end to end and are committed on branches. Both database migrations have since been applied and verified against production — the public cheque-image exposure is closed and credit control now enforces what the settings screen says.

Status today: functionally repaired and materially safer, but not production-proven. No end-to-end run through a browser or a device has happened. This is ready for UAT, not for customers.

The incident

Found while investigating your report that role permissions had disappeared. It was not a UI bug.

An automated QA run wrote into live production between 09:06 and 12:46 UTC. At its peak it had created 84 synthetic tenants against 17 real ones — five in six accounts in your database were fake.

Why the roles screen looked empty

The two Sales Executive roles were overwritten with the all wildcard. The roles page hides every checkbox when that flag is set, so a role granting unrestricted access renders identically to one granting none. Three real people — including two field reps in a customer’s account — silently held full admin rights, payment approval included.

The original permission sets were not recoverable. There is no audit table on employee_roles, no entries in module_activities, and track_commit_timestamp is off. Nothing in the database knew what those roles held before. They were rebuilt from the permission registry to a 35-key field-sales set with your sign-off — a reconstruction, not a restoration.

What was done

  • Full pre-deletion snapshot preserved at docs/engineering/incidents/2026-08-14-qa-prod-pollution-snapshot.json.
  • All QA artifacts purged. Accounts went 101 → 17, roles 75 → 23, with zero QA rows remaining.
  • Both damaged roles rebuilt; wildcard removed; approval rights withheld.
  • Your three genuine August 13 payments verified intact.

The unaddressed risk is process, not data. Nothing prevents this recurring — no separate QA project, no guard against test harnesses pointing at the production URL, and no audit trail that would let you reconstruct roles next time. That is the single most valuable thing to fix this week.

What was broken

Every item below is a pre-existing defect found during this review, not a regression introduced by it.

Blocking — the module could not function

Critical Web payment creation wrote to three non-existent columns

The form inserted attachment_url, attachment_name and attachment_type onto payments. None exist — attachments belong in the separate payment_attachments table. PostgREST rejects unknown columns, so every web payment save failed. The detail page read the same phantom column, so attachments never rendered either.

Fixed — attachments now write to and read from the correct table.
Critical Mobile collection would have failed on every attempt

The insert named date, created_by, gps_lat and gps_lng; the real columns are payment_date, user_id, latitude, longitude. The NOT NULL payment_type was omitted entirely. The customer dropdown selected contacts.outstanding_balance and the type dropdown filtered on payment_types.active — neither column exists, so both lists came back empty. The detail screen embedded a foreign key that does not exist (payments_created_by_fkey) plus four more wrong columns.

This code had never been committed or run against the real schema.

Fixed — payload and queries rewritten against the actual schema; typechecks clean.
Critical Permission gate checked a key no role holds

The form required add_payments; production roles carry create_payments. Owner and admin bypass the check, which is why it never showed up in your own testing — every non-admin user was refused.

Both spellings genuinely coexist in production. Rather than renaming stored keys — installed APKs check the legacy spelling and cannot be updated retroactively — permission lookup now resolves both directions. The rename migration that would have broken those builds is deleted.

Fixed — aliasing in rbac.ts, covered by tests.

Security and money — validated, awaiting your approval

Critical Credit control has never blocked anything

The settings screen writes payment_settings.credit_limit_enforcement. The database trigger reads payments.creditLimitAction. Different parent object, different key name — so the trigger always fell back to warn, for every tenant, however the screen was configured.

Proven against production: with “Block Orders” selected, a 999,999 order against a 1,000 credit limit inserted without complaint. Writing the trigger’s own key blocked it correctly — the logic works, nothing ever fed it.

Applied & verified — 20260814200000_fix_credit_control_settings.sql. Re-tested after apply: over-limit blocked, within-limit allowed, zero-limit enforced, null-limit unrestricted.
Critical Cheque images are publicly readable

The payment_attachments bucket is public, with an Allow public view policy granted to the public role and no size or MIME restriction. Anyone holding or guessing an object URL can read any tenant’s proof-of-payment images — cheques, bank receipts, UPI screenshots.

Applied & verified — bucket private, 10 MB and MIME limited, three account-scoped authenticated policies. Confirmed no remaining policy can match the bucket.
Critical Turning approval off makes collection impossible

With approval_required false, clients create payments already marked Approved — but the insert guard demands the approve_payments permission for that status. Any account that switches the setting off silently locks out every field rep. A latent trap: no account has flipped it yet.

Applied & verified — with approval off, a pre-approved payment now inserts cleanly.
Critical The security fix nearly shipped without closing the hole

The migration was written to drop policies named Allow public view and Allow authenticated uploads — the names in the original bucket migration. The policies actually present in production were named Public Access, Authenticated users can upload attachments and two more.

Dropping names that do not exist succeeds silently. Had this been applied as written, the bucket would have gone private while Public Access — a SELECT granted to the public role across the whole bucket — survived, and the exposure would have stayed open behind an apparently successful migration. Caught by reading the live policy list before applying rather than trusting the repo.

Corrected before apply — verified after: exactly one SELECT policy can match the bucket, scoped to account members.
High QA residue in four customers’ credit settings

Found while checking that no tenant would start blocking orders unexpectedly: hiren patel, Sahil Gohel, Pratik Maru and Next Innovation all carried settings.payments.creditLimitAction = "block", timestamped inside the QA window. The harness had written enforcement config into four real customers’ accounts, and the first purge only removed rows, not settings.

Harmless today — none of those tenants has a customer with a credit limit set, and the trigger exits early without one. It would have started blocking their orders the moment they set their first limit, with nothing in the UI explaining why.

Removed — all 17 tenants now resolve to the safe warn default.
High Mobile would have auto-approved the rep’s own cash

approval_required defaulted to false on mobile and true on web. Sixteen of seventeen accounts have never set the flag, so the same collection would be Pending from the office and Approved from the field — the collecting rep clearing their own money, which is exactly what separation of duties exists to prevent.

Fixed — mobile now fails safe to requiring approval.

Business logic — missing and weak

These are product decisions, not defects. I have deliberately not changed financial semantics without your call.

Decision An approved payment can never be reversed

The transition table makes Approved terminal, and the UI only offers actions while a payment is Pending. So a payment approved in error — wrong customer, wrong amount, a cheque that bounces next week — is permanent, and permanently understates what that customer owes.

The trigger contains a rule reading “Approved payments are read-only, except for cancellation” and PROJECT.md documents soft-delete via Cancelled — but the transition table blocks it first, so that intent is dead code. For a module whose entire job is money, there is currently no correction path at all.

Recommendation: allow Approved → Cancelled for cancel_payments holders, with a mandatory reason, and show a reversal on the customer ledger rather than editing history.

Not changed — needs your ruling before I touch settled money.
High Seven of eight payment settings do nothing

Only approval_required is read anywhere in either codebase. require_attachment, require_notes and require_reference are never referenced outside the settings screen — a manager can mandate proof-of-payment and reps will never be asked for it. The four credit settings are read under different key names. Mobile compounds it by looking for show_reference / show_notes, which nothing writes.

Credit keys fixed in the pending migration. The three require_* toggles still need wiring or removing.
High Outstanding counts only Closed orders

A customer can take delivery of goods and owe nothing on paper until someone closes the order. Credit limits are therefore enforced against a number that lags reality, and a rep can keep selling to a customer who is already over their ceiling.

Recommendation: decide explicitly what creates a receivable — dispatch, or order closure — and apply that definition in the trigger, the financial card and the reports together.

Not changed — this is a definition of receivable, and it is yours to set.
Medium Ageing is measured from sync time, not order time

Overdue calculations use orders.created_at, which records when the row reached the server. For an order written offline and synced days later, the customer is credited with days they never had. The fix is a client_created_at stamped on the device — the same gap already identified for Module Automations.

Not changed — needs a schema addition and a mobile release.
Medium Nothing ties a payment’s customer to its tenant

There is no constraint requiring contact_id to belong to the same account_id. Confirmed in testing: a payment can be inserted against another tenant’s customer. Row-level security stops the row being read across tenants, and the UI only offers own-account customers — but the product ships API keys, and this is the kind of hole that only shows up once someone integrates.

Not changed — wants a composite foreign key; worth doing with the next migration.
Low Client and database disagree on permission aliasing

Application code now resolves add_/create_ in both directions; the database has_permission function does not. Nothing exploits the gap today — triggers only check approve_, cancel_ and manage_ keys, which have no legacy spelling — but the two layers should agree before someone adds a check that does.

Documented, not changed.

What is genuinely good

The design of this module is better than its execution. These parts I would not change.

Solid Payment numbering
Allocated from an atomic per-account counter in a single upsert. No race, no gaps under concurrency, correctly scoped per tenant. An earlier MAX() + 1 version — which would have raced and crashed on the legacy number format — was never deployed; that file is now a documented no-op so nobody revives it.
Solid Status state machine, enforced in the database
Terminal states hold, invalid transitions are rejected, and approved payments cannot have their amount edited. Verified directly: Approved → Pending, amount edits on approved rows, negative amounts, zero amounts and invalid status values were all correctly refused. Enforcement sits in the database rather than the UI, so the API and mobile inherit it for free.
Solid The dual-amount model
Separating what a rep collected from what an approver verified is the right shape for field collection, and it handles the real cases — short cash, part-honoured cheques. It now needs to be applied consistently: the overdue check was summing the collected amount while the UI used the verified one.
Solid Offline sync architecture
The queue is genuinely generic — payments needed no new machinery, and the upload-then-substitute step extended cleanly to private buckets. Dead-lettering and the client-generated idempotency key are the right instincts for a field app on bad networks.
Solid The permission vocabulary itself
The registry draws the right distinctions — collect separate from approve, view-outstanding separate from view-credit-limit, override as its own grant. It is a well-designed model that was simply not being consulted correctly.

What should be removed

ItemWhy
receipt_number, receipt_generated, invoice_id, erp_reference, erp_sync_status Five columns on payments, all null in every row, referenced nowhere except a TypeScript interface. Speculative ERP scaffolding — drop them until an integration is real.
The three require_* settings They promise enforcement that does not exist. Either wire them into both clients or take them off the screen; a toggle that does nothing is worse than an absent one.
The “Ready for Pilot” claim It lives in commit a03b22a’s message, not in a file, so it cannot be edited without rewriting pushed history — not worth it. The real gap is that PROJECT.md carried no status line at all; an accurate one has been added so the next person reads the state rather than the sales pitch.
Duplicate status trigger trg_payment_status_transition and trg_enforce_payment_status_transition both ran the same validation on every update. Harmless while validation-only — a real problem the moment it gains a side effect. Consolidated in the pending migration.
The permission field on mobile’s module manifest The drawer never reads it, so every entry shows to everyone regardless. The new Payments screen gates itself; the manifest field should either be honoured or dropped so it stops looking like protection.

How this was tested

The module had zero test coverage: 68 test files in the web suite, none touching payments — for the only module that handles money.

Automated

39 new tests across three files, covering the areas where a silent error costs real money. The suite now stands at 942 passing across 71 files.

Against production, inside rolled-back transactions

Business rules were exercised directly against the live database in transactions that roll back, so nothing persisted — deliberately, given how the day started.

  • Status machine: 7 of 8 cases behaved correctly; the failure exposed the irreversibility gap above.
  • Numbering: sequential and gapless under repeated inserts; duplicates correctly rejected.
  • Credit limits: verified at the boundaries — under, exactly at, over, zero-limit, and no-limit.
  • Permission model: confirmed all three restored users can collect and none can approve.
One correction worth recording. My first credit-limit run reported the rule working. It was not — the test inserts were failing on an unrelated wrong column name, and a catch-all handler was reading that failure as “correctly blocked”. Capturing the actual error text showed the opposite: credit control had never blocked anything. A test that passes for the wrong reason is worse than no test, and it is worth assuming other green results in this codebase deserve the same scrutiny.
