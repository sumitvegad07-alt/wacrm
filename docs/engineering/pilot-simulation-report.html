Recommendation — Conditional GO

GO for a supervised pilot with one finance user. NO-GO for unsupervised production.

The financial engine is genuinely sound. Credit control passed all six modes, credit-days ageing passed, and the outstanding figure reconciled to the rupee across 20 customers, 100 orders and 50 payments — per customer and at account level. Money flows in correctly.

What fails is money flowing backwards. Nothing that has been approved or closed can be undone: approved payments are terminal, closed orders are terminal, and the web Cancel button calls a database function signature that does not exist, so it errors before it starts. A pilot will produce mistakes on day one, and today there is no in-product way to correct one.

Two fraud vectors are also open in the customer master, both of which let a field rep quietly change what a customer owes.

Critical findings

Each was reproduced by executing the workflow, not by reading code.

1. The web Cancel button cannot work

The Cancel dialog calls update_payment_status with a p_cancellation_reason argument. The deployed function takes four parameters and that is not one of them, so Postgres rejects the call before any business logic runs.

Finance clicks Cancel, fills in the mandatory reason, confirms — and gets an error every time. There is no working path to cancel a payment from the product.

executed → function update_payment_status(uuid, unknown, unknown, unknown, unknown) does not exist

2. "Mandatory cancellation reason" does not exist anywhere

There is no cancellation_reason column on payments, no parameter on the RPC, and no constraint. Cancelling with no reason at all succeeds silently.

The feature was announced in the shipping commit as "mandatory cancellation reasons and audit logging". A cancelled payment currently records who and when, but never why. For a module whose purpose is cash custody, that is the audit trail that matters most.

executed → cancel with no reason: ALLOWED, status now Cancelled, reason recorded nowhere

3. Approved money and closed orders are both irreversible

Approved is terminal for payments; Closed is terminal for orders. Neither can move to Cancelled. A payment approved against the wrong customer, or a cheque that bounces next week, permanently understates what that customer owes — and a closed order booked in error permanently overstates it.

In a seven-day pilot with real reps, both will happen. The only correction available today is direct database surgery.

executed → Approved → Cancelled: rejected · Closed → Cancelled: rejected ("Closed is terminal")

4. A field rep can rewrite what a customer owes

Credit Limit is properly protected — a rep is blocked, a finance manager is allowed. But Opening Balance and Credit Days have no such guard. Running as an actual field rep, both were changed successfully.

The fraud is straightforward: reduce a customer's opening balance to hide a shortfall, or set credit days to 365 so an overdue account never surfaces on any report. Both directly manipulate the receivable, and neither is logged as a financial change.

executed as Field Sales Rep → opening_balance 5000 → 1: ALLOWED · credit_days 30 → 365: ALLOWED

Business logic findings

Backdating a collection is unvalidated

A rep recorded a payment dated 400 days in the past with no warning or block. Combined with the credit-days engine reading that date, a backdated collection can be used to make an overdue account appear settled in an earlier period.

Recommendation: constrain payment_date to a sensible window — not in the future, not more than N days back without a permission.

No business-level duplicate detection

Ten identical collections — same customer, same amount, same day — were accepted without comment because each carried a new id. The idempotency key correctly prevents a technical duplicate from a retry, but not a human one from a rep saving twice after a slow screen.

Recommendation: warn on a same-customer, same-amount collection within a short window. Do not block it — legitimate repeat payments happen.

The lifecycle has no Draft state

The brief assumed Draft orders. OZZO starts at Pending, so an order is live from the moment it is created. If reps need to build an order across a visit before committing it, that state does not exist today.

What is genuinely solid

Stated as plainly as the failures.

  • Credit control is trustworthy. All three modes behave correctly, the boundary case (landing exactly on the limit) is right, the override permission works and every override is written to the activity log. This was non-functional twelve hours ago; it is now the strongest part of the module.
  • The books reconcile. Three independent calculations of outstanding agreed exactly, and the sum of 20 customer balances matched the account rollup to the rupee under a full week's transaction load.
  • Separation of duties holds. A field rep could not approve, reject or cancel a payment, could not create one pre-approved, and could not raise a credit limit. Every refusal came from the database, not the interface — so the API and the mobile app inherit it.
  • Partial dispatch is well built. 50 of 100 units produced Part Dispatch; the remaining 50 auto-closed the order and it flowed into outstanding immediately.
  • Numbering does not collide. 100 orders and 50 payments, all uniquely numbered, including under a rapid burst.
  • Retry safety is real. A replayed offline queue item and ten rapid saves sharing one key both produced exactly one payment.

Conditions for GO

In the order they block a pilot.

  1. Make cancellation work. Add the missing RPC parameter and the cancellation_reason column, enforce it as mandatory, and allow Approved → Cancelled for holders of cancel_payments. Until this lands, finance has no way to fix a mistake.
  2. Guard Opening Balance and Credit Days the same way Credit Limit already is. Two lines of trigger logic close both fraud vectors.
  3. Decide on closed-order reversal. Either allow Closed → Cancelled or define a credit-note flow. A pilot will book a wrong order in week one.
  4. Constrain payment_date to stop silent backdating.
  5. Build and hand-test the APK. Phase 7 is genuinely unproven, and mobile collection is the product's reason to exist.

Items 1 and 2 are small and would move the score to roughly 88. I would run the pilot after those two, with one trusted finance user watching the approval queue daily, and I would not put a second customer on it until the mobile phase has actually been executed on a device.
