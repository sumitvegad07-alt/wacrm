Root cause analysis

Traced UI → API → RPC → trigger → constraint → schema, as instructed. Each failure had a different cause; they were not one bug with four symptoms.

S12b — the Cancel call never reached the database

The dialog sends five named arguments. The deployed function accepted four. PostgREST resolves an RPC by its argument names, finds no match, and rejects the request before any business logic runs.

UI handleCancel({cancellation_reason}) → rpc(update_payment_status, 5 args) → PostgREST → function update_payment_status(uuid,unknown,unknown,unknown,unknown) does not exist

Fix: the four-argument function was dropped and replaced with a five-argument one. Dropped, not overloaded — keeping both would have made every four-argument call ambiguous.

S12 — the reversal was forbidden two layers down

Even a resolvable call could not have worked. payment_status_transition_allowed() listed no transition out of Approved, so the trigger's own rule — "Approved payments are read-only, except for cancellation" — was unreachable code guarding a path the table below it refused.

Fix: ('Approved','Cancelled') added. Approved still cannot return to Pending or be Rejected after the fact; cancellation is its single audited exit.

S12c / S13 — there was nowhere to put a reason

No cancellation_reason column, no RPC parameter, no constraint. The shipping commit advertised "mandatory cancellation reasons and audit logging"; none of it existed.

Fix: cancellation_reason, cancelled_by and cancelled_at added and populated automatically. The mandatory check lives in the trigger, not only the RPC — the mobile app writes the payments table directly through its sync queue and never calls the RPC, so a rule enforced only there would not exist for the field.

S3b / S3c — one field was guarded, two were not

enforce_customer_credit_permissions() checked only credit_limit. opening_balance and credit_days passed through untouched, so a rep could restate what a customer owed or push an overdue account out of sight.

Fix: both now sit behind permissions that already existed in the registry — manage_customer_credit for credit terms, edit_opening_balance for the carried balance. No new permission was invented where a correct one was already defined and unused.

S19c — payment_date had no bounds at all

Any date was accepted. Since the credit-days engine ages from that date, a backdated collection can make an overdue account appear settled in an earlier period.

Fix: future dates refused outright. Anything older than the account's allow_backdate_days (default 30) requires the new backdate_payments permission — gated rather than banned, because a cheque handed over last week and entered today is legitimate.

S27b — only the primary key stood between finance and ten identical payments

The idempotency key correctly stops a technical duplicate from a retried queue item. It says nothing about a human one: ten saves with ten new ids and identical content were all accepted.

Fix: check_duplicate_payment() is called before save on web and mobile, and an insert trigger logs a warning regardless — so a duplicate arriving from the API or an offline sync is still visible to finance afterwards. Warn, never block: a genuine second collection at the same counter must not be refused.

Phase 3 — Order reversal analysis

Analysis only, as instructed. Nothing was implemented and S6 remains failing. Context: there is no credit note, return, invoice or ledger table in the schema today, so option B is entirely greenfield.

Option A — allow Closed → Cancelled

Mirrors what was just built for payments

  • Accounting: the order leaves the Closed set, so outstanding drops by its full value immediately. Clean when the order was booked in error; wrong when goods actually shipped and only part is coming back — it erases the whole sale rather than recording a return.
  • Reporting: historical revenue changes retroactively. A month already reported to the founder can move after the fact, with no artefact explaining why.
  • Credit control: correct and immediate — the customer's limit frees up.
  • Complexity: lowest. One transition entry, a mandatory reason, and the audit columns — perhaps half a day, reusing exactly the pattern now proven for payments.
  • Risk: a dispatched order can be cancelled while stock has physically left the warehouse, putting the books and the godown out of step.

Option B — credit note

Recommended, with Option A as an immediate stopgap

  • Accounting: correct. The original order is never altered; a separate negative document offsets it in full or in part. Partial returns — the common real case — are representable, which Option A cannot do.
  • Reporting: history is immutable. Revenue for a closed month stays as reported, and the reversal appears in the period it actually happened. This is what an auditor expects.
  • Credit control: needs the outstanding formula extended to opening + closed orders − approved payments − credit notes, touching the trigger, the financial card, the dashboard and the reports together.
  • Complexity: highest. New table, numbering sequence, approval workflow, permissions, UI, mobile surface, report columns. Realistically one to two weeks, and it is a module rather than a fix.
  • Risk: too large to land before a pilot; shipping it half-built would be worse than either alternative.

Option C — reversal window

The pragmatic middle

  • Allow Closed → Cancelled only within N days of closure, only for a reverse_orders permission, only when no dispatch exists against the order, and always with a mandatory reason.
  • Accounting: same as A, but bounded to the window where a mistake is still plausibly a data-entry error rather than a commercial return.
  • Reporting: retroactive change is confined to the current period, so closed months stop moving.
  • Credit control: identical to A.
  • Complexity: low-to-moderate — one to two days on top of A.

Recommendation: ship Option C now to unblock the pilot, and put Option B on the roadmap before a second customer. C gives finance a correction path for the mistake a pilot will actually produce — an order closed on the wrong customer in week one — without pretending the product has a returns process it does not have. Pure Option A I would avoid: cancelling a dispatched order with no guard is how stock and books drift apart.

Conditions before a rep touches this

  1. Decide A, B or C on order reversal. The only remaining functional gap.
  2. Click the cancel flow once, in a browser. Approve a payment, cancel it with a reason, confirm the customer's outstanding rises by that amount and the reason appears on the record. Fifteen minutes, and it converts the largest unproven area into a proven one.
  3. Build the APK and collect one real payment on a phone, including in airplane mode. Nothing about mobile has been executed.
  4. Grant permissions deliberately. backdate_payments is new and unassigned; cancel_payments and edit_opening_balance should sit with finance only. Check the roles screen before day one rather than discovering it mid-pilot.
  5. Then run the pilot supervised, with finance reviewing the approval queue and the new duplicate warnings daily.
