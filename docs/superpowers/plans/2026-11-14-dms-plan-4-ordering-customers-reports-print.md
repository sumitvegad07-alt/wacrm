# OZZO DMS Plan 4 — adding customers, placing orders, reports, print and export

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development
> (recommended) or superpowers:executing-plans to implement this plan task-by-task.
> Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn the read-only portal into one a distributor can actually run their business
from: add a shop, place an order, read four reports, and print or export any of it.

**Architecture:** Every new rule is a `security definer` function in the CRM's database,
called by the portal through `lib/portal/api.ts`. The portal gains no table grants and no
privileged key — the two properties Plan 2 was built around. Writes reuse the engines the
CRM and the Android app already call (`create_order`, `calculate_order_pricing`,
`detect_eligible_schemes`); the portal functions are gates in front of them, never
replacements.

**Tech Stack:** Postgres 17.6 (Mumbai `ltigfpywdbfilsagtpyd`), Next.js 16.2.6 / React
19.2.4 / Tailwind 4 in `C:\Wacrm\ozzo-dms`, vitest, `tools/pgsql` throwaway cluster.

**Spec:** `docs/engineering/specifications/ozzo-dms-product-v1.md` §7, §8, §11, §12, §17.
Task 1 is NOT in that spec — it answers a question the founder asked on 2026-11-14 and
amends §4. Task 5 likewise amends §11.

## Global Constraints

* **Nothing is pushed or deployed until the founder says so.** His instruction, recorded in
  Plan 2: *"Once we will completely develop everything test everything than we will Push
  everything to live."* `C:\Wacrm\ozzo-dms` is a local repo with no remote.
* **`.env.local` points at PRODUCTION.** Never run a migration or a script against it. SQL
  is proven on the throwaway cluster — `PGDATA_DIR=/tmp/ozzo-pgtest bash
  scripts/run-db-tests.sh`, ~11 minutes, 46 known migration errors — and then written into a
  `docs/RUN-THIS-SQL-*.md` for the founder to paste into the Supabase SQL editor. The SQL in
  that document must be byte-identical to the migration.
* **The portal app never holds a service-role key**, in any file, including a comment or
  `.env.local.example`. `lib/supabase/no-privileged-key.test.ts` fails the build otherwise.
* **The portal reads no table directly** — only the `portal_*` functions, by name.
  `app/portal-screens.test.ts` fails the build otherwise.
* **No employee is ever named to a distributor** (§17 q4).
* **Dates are account-local.** Convert `AT TIME ZONE public.account_timezone(account_id)`.
  Never `toISOString()`. `DATE` columns are already account-local — do not convert those.
* **Money arrives from PostgREST as strings** (`numeric(15,2)`). `lib/portal/types.ts` types
  it as `Money = number | string | null` and `money()` is the only thing that renders it.
* **The look is the CRM's, copied not approximated.** Any new screen uses the primitives in
  `components/ui` and `components/shared`; `app/design-system-parity.test.ts` pins the
  tokens. If the CRM's design changes, re-copy the files rather than editing them here.
* Fixes apply to **all tenants** by default.
* Every behaviour below that is a rule must be proven by a scenario in
  `supabase/tests/`, and each security rule must be **mutation-checked**: remove the rule,
  watch a named scenario fail, put it back.

## The four questions this plan answers

Asked by the founder on 2026-11-14, after seeing the portal for the first time.

### 1. "Do you think we need to provide options to create new customers?"

**Yes — add only, behind a tenant setting that defaults to OFF.** Three reasons, in order
of weight:

1. **Ordering does not work without it.** Task 2 lets a distributor place an order for one
   of their own shops. A shop that is not in the system cannot be ordered for, so the first
   new retailer turns into a phone call to the company — which is the exact cost the DMS
   exists to remove. Every competitor allows it.
2. **The database already prevents the thing that makes people say no.** The usual
   objection is duplicate and junk master data;
   `idx_contacts_account_phone_normalized` refuses a second customer on the same phone
   number outright, for every writer including this one.
3. **The dangerous fields can simply be withheld.** A distributor never gets to set a credit
   limit, a price list, an area or territory, a customer code or a buying status. Those are
   the company's levers over its own risk, and the portal form does not contain them.

What they get is a six-field form — name, company, phone, address, city, GSTIN — and the
row lands with `parent_id` forced to themselves, the territory inherited from their own, the
customer code auto-generated by the existing trigger, and `created_via = 'portal'` so the
company can see at a glance which customers came in this way.

Default OFF because a company that wants its field team to own every customer record should
not have this appear underneath them after an upgrade. The same reasoning as
`reporting_hierarchy` and `secondary_sales`.

**What is deliberately NOT included:** deleting a customer, editing a customer the company
created, and changing a parent. A distributor may correct the name, phone, address, city and
GSTIN of a customer **they themselves added**, and nothing else.

### 2. "Currently there is no option for placing a new order"

Correct, and it is the single biggest gap. Spec §7, built as Task 2. It is a gate in front
of `create_order` — not a second order path — so pricing, numbering, the
primary/secondary classification, idempotent replay and the variance check are the ones
already trusted by the CRM and the Android app. Schemes are included (§7.4) because without
them a distributor placing their own order gets a **worse price** than if a salesman had
typed the identical order, and they will notice.

### 3. "There are no reports"

Correct. Four fixed reports, spec §11, built as Task 5. The existing report engine is **not**
opened to the portal: it is wired to employee roles, permissions and `report_registry_*`,
and pointing it at an outsider is a bigger and riskier job than four purpose-built
functions.

### 4. "There is no printing or exporting option"

Correct, and it is not in the spec at all — it is added here. Two different needs:

* **Print one order** on A4 or A5, which is what a distributor hands to their own customer
  or keeps for their file. The CRM already has an A4/A5 print stylesheet and a print route;
  the portal gets the same one, fed by `portal_order_detail`.
* **Export a list** to CSV — every table, and every report. CSV rather than XLSX: `xlsx` is
  a 500KB dependency on an app a distributor may open over a phone connection, and every
  spreadsheet on earth opens CSV.

### 5. "No branding of OZZO… same to same as our admin portal"

**Done on 2026-11-14**, commit `8287fb1` in `C:\Wacrm\ozzo-dms`. Not part of this plan.

- [x] **Step 3: Write the migration**

```sql
ALTER TABLE public.contacts
  ADD COLUMN IF NOT EXISTS created_via text NOT NULL DEFAULT 'app'
    CHECK (created_via IN ('app','import','portal','api'));

CREATE OR REPLACE FUNCTION public.portal_can_create_customer()
RETURNS boolean LANGUAGE sql STABLE SECURITY DEFINER SET search_path = public AS $$
  SELECT coalesce(
    (SELECT (a.settings->'dms_settings'->>'allow_customer_create')::boolean
       FROM public.accounts a
       JOIN public.contacts c ON c.account_id = a.id
      WHERE c.id = public.portal_caller()),
    false);
$$;
```

`portal_create_customer` then, in order: resolves `portal_caller()` and returns null if it is
null; returns null unless `portal_can_create_customer()`; inserts with `account_id` and
`parent_id` taken from the caller's own row and **never from a parameter**; leaves
`credit_limit`, `price_list_id`, `area_id` and `territory_id` untouched so the company's
defaults apply; sets `created_via = 'portal'`. Grant `execute` to `authenticated` only.

The customer code is NOT generated here — the existing auto-code trigger does it, and a
second generator is how two code series start.

### Built 2026-11-15 — what the build changed

The five checks are as planned. Three interface changes, each for a reason the
plan could not have known:

* **`portal_place_order` returns `jsonb`, not `uuid`** — `{order_id,
  order_number, pricing_status, idempotent_replay}`. The screen has to tell the
  reader the order number, and a replayed submit has to be distinguishable from
  a new one; both would otherwise need a second round trip.
* **It takes `p_accept`, and NOT `p_order_schemes`.** The plan had the screen
  send the schemes, as the admin app's browser does. That cannot be allowed
  here: `scheme_discount_amount` is money. So `portal_apply_schemes` (new) asks
  the detector itself and applies what it finds, and `p_accept` carries only
  TICKS — `"<position>:<scheme_id>"`. Free goods need a tick because
  `detect_eligible_schemes` returns `default_selected = false` for them on
  purpose, exactly as the admin app makes a salesman tick them; money discounts
  are applied unasked. A tick naming an offer that does not apply is ignored
  (W13f).
* **`portal_normalize_lines` (new) is the only shape the browser may send**:
  product, quantity, entered unit. The conversion factor is read from
  `product_unit_conversions` and the tax mode from the account's own order
  settings, because a forged factor of 1 prices a box as a piece and the engine
  would price it faithfully (W15).
* **An extra rule the plan did not list, and it was a leak:** `create_order`
  replays by id and returns the existing ORDER NUMBER, so without an ownership
  check on the replay branch a guessed uuid would have handed an outsider a real
  order number from another tenant (W11b).
* **W8 reads differently from the plan.** `create_order` only sets
  `pricing_status = 'review'` for `offline_sync`; an online order logs the drift
  and stays confirmed. The gate therefore holds the order for review itself when
  the quoted total and the engine's total disagree — the saved figure was never
  in doubt, the point is that the company sees the disagreement before dispatch.
* **Sales credit (spec §7.5) is built and defaults to the dealer's own rep.**
  `dms_settings.portal_order_sales_credit`: `dealer_salesman` (default) or
  `portal`. The default is not a guess: a portal login has no `profiles` row, so
  an order left in its name shows a blank salesman AND drops out of every list
  that scopes by `user_id` in the client — including the rep responsible for that
  beat. **The founder still has to confirm he wants that default.**
* The CRM side of Step 5 was already built (`f8a2bdd`, migration
  `20261107140000`): the Orders list has had its **Placed via** column and
  filter since Plan 2.
* 35 scenarios, W1–W18, all passing; eight rules mutation-checked.

## Task 6: Settings a distributor can set for themselves

Asked for by the founder on 2026-11-15: *"some of the settings option in DMS too where
they can mention their GST Details, their own logo, their own templates, Their own Custom
fields, Manage column, Theme settings similar to admin."*

Six things, and they are not one feature. Three are safe and cheap, one needs a
distinction drawn before it is built, and two should not be built as asked.

### 6a. Theme — yes, and it is nearly free

`lib/themes.ts` is already copied into the portal with all five accents, and the CRM's
picker is pure `localStorage` — no table, no tenant, no migration. A **Settings → Display**
panel with the accent swatches and the light/dark choice, exactly the CRM's.

### 6b. Manage columns — yes

The portal's `Column<T>` list is already the single description of each table, and the
export in Task 4 reads the same list, so a hidden column stays hidden in the CSV without
any extra work. Persist the choice in `localStorage` per device, **not** in the database:
the CRM's saved views ride on the employee engine, and a portal customer has no profile to
hang one from. A device-scoped choice is also the honest one — a distributor on a phone
wants fewer columns than the same distributor on a laptop.

### 6c. Their business details and their logo — yes, but as a PRINT PROFILE, never as an edit

This is the one that needs the distinction drawn before a line is written.

A distributor's GSTIN already exists: it is on their `contacts` row, put there by the
company, and it is the number **the company raises its invoices against**. Letting an
outsider edit that field means letting them change a tax identifier on documents the
company is legally responsible for. That is not a settings screen, it is a hole.

But the reason they want it is legitimate and different: when they print an order for
**their own** customer, the paper should carry **their** letterhead, because on that
document they are the seller. So:

```sql
ALTER TABLE public.contacts
  ADD COLUMN IF NOT EXISTS portal_print_profile jsonb NOT NULL DEFAULT '{}'::jsonb;
```

`portal_set_print_profile(p jsonb)` writes only that column, only for `portal_caller()`'s
own row, and only these keys: `trade_name`, `address`, `gstin`, `phone`, `email`,
`logo_path`. Anything else in the payload is dropped rather than refused, so a future key
cannot arrive by accident.

The Settings screen shows the **company-held** details — the GSTIN the company invoices
them against, their credit limit, their area — **read only**, with one line saying *"These
are held by your company. Ask them to change anything here."* Underneath, the print profile
they own. Two blocks, visibly different, so nobody believes editing the second changed the
first.

The logo goes to Supabase storage under `portal-logos/<account_id>/<contact_id>.<ext>`,
uploaded through a definer function that checks the caller — the portal gets **no** blanket
bucket grant. Cap it: 512KB, PNG/JPG/WEBP, and reject anything else by content type rather
than by extension.

**Tests:** the print profile cannot be written for another contact; the company-held GSTIN
is unchanged by any payload that names it; an upload for somebody else's contact id is
refused; a 2MB file is refused.

### 6d. Their own document templates — not in this plan, and here is the smaller thing instead

The CRM's template engine is storage, an editor, a renderer and per-account template rows.
Giving each distributor their own adds a whole new dimension — per **contact** templates —
through every part of it, and each one then needs a preview, a default, and a fallback when
it is broken.

Nine tenths of why they want it is **"my name and my logo on the paper I hand my
customer"**, and 6c delivers exactly that into the Task 3 print view. Build 6c, put it in
front of a distributor, and see whether the remaining tenth is still asked for. If it is,
it gets its own plan.

### 6e. Their own custom fields — recommend NOT, and build the opposite instead

A field a distributor invents would be created in the **company's** `custom_fields` table
and its values stored against the **company's** customers, orders and visits. It would then
appear in the company's own screens, its exports, its imports and its reports — and in the
four `*_custom_values` tables that were world-readable until 2026-11-15. Ten distributors
would invent ten different versions of "shop type", and the company would own all of them
forever.

The need underneath it is real, so meet it the other way round: **the company creates the
field and marks it "ask the distributor"**, and the portal's add-customer and order screens
show those fields. The company keeps one vocabulary, the distributor fills it in, and the
data is worth reporting on afterwards — which fields invented ten ways are not.

That is a small change to the existing custom-fields engine (one boolean on
`custom_fields`, a filter in two portal functions), and it belongs with Task 1 and Task 2
rather than in a settings screen. Costed here, built when the founder agrees the trade.
